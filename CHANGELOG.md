# Changelog

## 0.1.80 — 2026-08-31

### Fixed

- **`rules/ui-automation.md` claimed Done persists over a WebSocket. It is a plain observable HTTP POST** (`rules/ui-automation.md`, `skills/_reference/endpoints.md`, `skills/_scripts/hub_app_subscriptions.py`, `skills/sensor-onboarding/SKILL.md`). The rule is always-on and `endpoints.md` is read on demand, so the loaded context asserted a mechanism its own reference contradicted, and the wrong one won by default. This is distinct from the #131 gap, where the rule merely never *mentioned* Done: an omission an agent can research its way out of, versus a false statement it has no reason to doubt. Captured on 2.5.1.169 (hub `.17`, app 636, 14 settings): `[POST] /installedapp/update/json => [200] OK`, form-urlencoded, no WebSocket frame involved. The only socket on that page is `/eventsocket` driving the live log display, which is plausibly what made it look socket-driven. Replayed verbatim from `curl` and `updated()` ran — `unsubscribe`/`unschedule`/`initialize`, both app-state clocks stamped to the same instant, the `runEvery5Minutes` job rescheduled. The operative warning survives the correction intact and is now stated as what it always was: the hazard is the **full-form replace** (omitted settings are cleared), never the transport.
- **A JSON body to `_action_update` is a silent 200 no-op** (`skills/_reference/endpoints.md`, `rules/ui-automation.md`). The `/json` in the path invites `Content-Type: application/json`. That request returns 200, a body that is the config page HTML rather than an error or a `{"status":…}`, and executes nothing — no `updated()`, no `initialize()`, no re-subscribe, no schedules. It does not 400, does not 415, and never mentions the content type. The resulting state is **half-live, not dead**, which is what makes it dangerous: after freshly deployed code plus a JSON `_action_update`, `eventSubscriptions` read `power → powerHandler` (the *pre-existing* subscription, now dispatching into the *new* code), app state carried a fresh timestamp (written by the event handler, not by `initialize()`), and `scheduledJobs` was `null` — the new sweep never registered. Two of three surfaces look healthy, so an agent verifying by subscription-and-state concludes the commit worked while the app cannot act at all. **`scheduledJobs` is the load-bearing check**, and `hub_app_subscriptions.py` now reports it alongside the subscriptions for exactly that reason; the script does not judge it, since an app that schedules nothing legitimately has none. This failure also *reinforced* the stale WebSocket claim: hand-roll JSON, watch it silently do nothing, conclude Done must not be HTTP — which is the path that was taken before the real request was captured. The worked `_action_update` body shape is recorded too (three fields per setting, `checkbox[<name>]=on` for bools, a preceding `deviceList=<name>` for device multi-selects, double-encoded `pageBreadcrumbs`), which the existing `_action_remove` note did not cover. Closes #147.

## 0.1.79 — 2026-08-31

### Added

- **A dead attribute channel on a live multi-sensor defeats BOTH liveness rules at once** (`rules/state-vs-attributes.md`, `skills/_scripts/hub_device_events.py`). Grounded 2026-07-27: a contact/temperature/battery multi-sensor reported `contact = closed` while the window was **physically open**. Not a dead device — a dead *attribute*. Both existing mitigations pass it. Derive liveness from a monotonic attribute: temperature and battery were both advancing and `lastActivityTime` was current, so the **device** passes. Remember that an unchanged value emits no events: that is exactly the reasoning that makes `contact = closed` since two months ago look like a genuinely shut window, so the **value** passes. The confirming read was `GET /device/eventsJson/<id>` — **zero** contact events out of 33 retained, all temperature and battery. The radio, battery and temperature channels work; the reed switch reporting does not. New `hub_device_events.py` censuses the retained log per attribute and names the silent channels, with `--expect-attribute` to assert one is reporting; `command-*` rows are excluded, since a command being issued is not the attribute moving. A zero count is recorded as a **prompt to investigate, never proof** — the retained window is bounded by `maxEvents` (default 11 changes), so a steady channel on a short window and a dead one look identical there, and the value has to be compared against physical state to separate them. Also records the reasoning failure worth keeping: the frozen value was read as "the window has been shut for two months" because that story was physically plausible. A plausible physical explanation for a frozen value is not evidence — it is the hypothesis the check exists to test, which is the same trap `self-reported-vs-measured` names, arriving from the liveness side. Closes #141.
- **Generic Z-Wave Lock publishes the commanded MODE and discards bolt status** (`rules/driver-lifecycle.md`, `rules/state-vs-attributes.md`). Hubitat's built-in driver derives `lock` from `DoorLockCCOperationReport`'s **`current mode`** — what the lock was *told* to be — and throws away the same report's separate `bolt status`, `latch status` and `door status`. A motor that accepts the command and then stalls or backs out reports `mode: Secured` with the bolt retracted, and Hubitat publishes `lock = locked`. `refresh()` does not help: the truthful field arrives over the wire and is discarded on arrival. Grounded 2026-07-27: house armed 11:11:20 → garage lock reported `locked` 11:11:50 → the arming app announced all locks truly locked → door found **shut and unlocked** at 13:31, with every motion and presence sensor on the path silent 11:11→13:28, so nobody retracted it afterwards. The lock never threw the bolt and said it had. This is the highest-consequence instance of the `self-reported-vs-measured` shape: an attribute that is model output rendered identically to a measurement. `latchStatus` / `doorStatus` are recorded as **junk on Ultraloq** — a definitively shut door reports both `open` — so never gate an automation on them. `doorCondition` does reach a driver's `parse()` on the zwaveJS backend, and the bit mapping ships with the instruction to assert it against the hub's own zwaveJS decode of the same frame, because a first pass had the latch bit inverted and only that comparison caught it. Closes #136.
- **Room Lighting's scheduled off is gated on `state.active`, not on the lights** (`rules/room-lighting-shades.md`). When `active == false` the off fires, logs `Already Turned Off`, and sends **no `off()` command**. The light stays on and nothing anywhere reports a failure. It latches because RL subscribes `allOffHandler` to `switch.off` on its members, so **any** external off — physical switch, Alexa, HomeKit, a dashboard, a `runmethod` during maintenance — sets `active = false`, and a subsequent external **on** does not set it back; only RL's own activation path does. One off→on outside RL latches "the room is off" while the room is lit, and every scheduled off until the next real activation is a no-op. Grounded 2026-08-12: an instance with off cron `0 0 23 * * ?` logged `Turn Off Event: time` / `Already Turned Off` at 23:00:00.11 and the lights burned until killed by hand at 23:20; the latch had been set at 20:53 by on/off testing while re-pointing the instance. It self-heals at the next activation, so it presents as a one-off — it is not, it recurs on every external off→on and is silent every time. Two traps inside it: `prevRunTime` advancing is not evidence the off happened (the cron fires and the handler runs; the no-op is downstream of both — the same success-shaped lie as `runmethod` returning `success: true`), and "switch turns on" in `onMeans` is not a self-heal (it subscribes `switch.on → actHandler` on the separately-picked `switches` list, not on the room's own lights). The fix is the `doTurnOff` bool on `offMeansPage → optionsOffPage`, verified by A/B on the real `offHandler` under an identical desynced state. Closes #137.
- **`state.endPoints > 0` is not proof the child devices exist** (`skills/_reference/parent-child-devices.md`, `rules/driver-lifecycle.md`). Grounded 2026-08-12: a Zooz ZEN14 outdoor double plug began erroring `No device for endpoint (1)/(2). Press Configure to create child devices.` on the first refresh after the hub updated to **2.5.1.152**. Every error forwarded to notifications, so it read as a device fault. It was not — the device had carried `state.endPoints = 2` for a month while `refresh()` sent a per-endpoint `switchBinaryGet` every 6 h with no errors, and the parent's `on()`/`off()` targets endpoint 0 and drives both outlets, which is what Alexa, HomeKit and Maker API all use. Nothing was broken before or after. The errors fire only on an **inbound** report carrying a non-zero endpoint, so the endpoint-encapsulated replies had previously not been reaching the driver with their endpoint; the dispatch mechanism is recorded as **inference from a tight correlation across the restart, not measured**. The diagnosis trap is worth the space: reading the driver you would conclude Configure cannot help, since `createChildDevices()` is called only from the `MultiChannelEndPointReport` handler and the probe requesting that report fires only when `state.endPoints == null` — which it isn't. Configure works anyway, because `configure()` → `clearVariables()` → `state.clear()` nulls `endPoints` and the probe re-fires. That indirection is the whole answer and it is invisible from the two obvious call sites. `driver-lifecycle` gains the general shape: a platform update can change what reaches `parse()`, the zwaveJS backend split being the other recorded instance. Closes #140.
- **Swap Device: the new hardware lands in the OLD record** (`rules/device-lifecycle.md`, `skills/_reference/endpoints.md`). Grounded 2026-08-30 on 2.5.1.176, replacing a dead Zigbee leak sensor with a Z-Wave LR one. Device `119` had been a hub-mesh mirror since the beginning; after the swap it is a native `Zooz ZSE42`, `deviceNetworkId 0179`, `type usr`, and the freshly paired device (`1688`) no longer exists. Every app, dashboard and subscription bound to `119` keeps working with no re-selection, which is the point — but **the id you paired is not the id you end up with**. Three pieces of residue all read as broken and none are: `currentStates[*].deviceId` keeps the **donor's** id on every row until the next report overwrites it (the state rows moved across and kept the stamp they were created under, and it is the first thing you see in `fullJson`); the event log stays with the surviving record, so `GET /device/eventsJson/119` showed the mirror's `hubMeshDisabled` history and **none** of the new sensor's first readings, which had been logged under `1688` and went with it; and the actual binding proof is elsewhere — `GET /hub/zwaveDetails/json` → `nodes[].deviceId`, node `377` → `deviceId 119`, which is what says where inbound frames land. Closes #134.
- **Deleting a HomeKit-exported device leaves an orphan accessory frozen at alarming values** (`rules/device-lifecycle.md`). Grounded 2026-08-30 on 2.5.1.176. Both hub-side surfaces were correct with no action: the bridge app's `authorizedDevices` had dropped the deleted device, and the live HAP database served 54 accessories with no `HUBITAT<id>` among them. The **controller** still listed it, serving `LeakDetected = 1` (wet), `battery_level = 0` with `StatusLowBattery = 1`, and a temperature service reading `-0°F`. So a decommissioned sensor presents in Home as a live leak with a flat battery — the most attention-grabbing state the accessory has, and pure residue. Two things make it hard to clear: a bridged accessory **cannot** be removed through the HomeKit API (`HMHome` only removes non-bridged accessories or an entire bridge), so it is a controller-side manual action; and the serial characteristic `HUBITAT<hubitatDeviceId>` is **not unique across hubs** — two hubs in one home can mint the same serial, and here the orphan and its replacement both read `HUBITAT119` on different bridges, with capability shape (the Zigbee original carried a temperature service, the Z-Wave replacement does not) as the distinguishing evidence. The bridge app also retains `disableAccessoryTrait|<id>|…` and `assignAccessoryClass|<id>|…` rows for the deleted id, which would apply to whatever device next takes that id on that hub. `device-lifecycle` **Verify after removing or renaming** already said not to assume the hub auto-pruned every reference type; this is the twist where the hub *did* prune and the external controller did not. Closes #135.

Two examples showed `--device <id>` / `--app <id>` with no `--hub` or `--ip`, so following them exits 2 on a config error rather than running the check. Same defect class Copilot caught in the `/device/update` examples in #143; swept every invocation across the rules, skills and references this time rather than fixing the two that were reported.

The dated 2.5.1.152 / Zooz ZEN14 incident is archived in the `#140` entry above and in `parent-child-devices.md`, which loads on demand; the rule keeps the general shape. Advisory `context-writing-style` findings, folded in rather than deferred — this was the last round of the batch, so there was no later one to fold them into.

Written rather than left as prose because the check is a deterministic read-group-count, the same ruling `script-delegation` produced for the `/device/update` round-trip in #143 and the subscription read in #146. ## 0.1.78 — 2026-08-30

### Added

- **`skills/_scripts/hub_app_subscriptions.py`** — reports an installed app's live `eventSubscriptions`, with `--attribute` to filter and `--expect-device` to assert a device is subscribed after a config Done. The first draft of the sensor-onboarding step embedded a `curl | python3 -c` pipeline; the policy reviewer called it correctly under `script-delegation`, the same ruling the `/device/update` round-trip took in #143. The assertion is **presence of the expected device, never a count delta** — the issue proposed `+1` exactly, which is not generally valid: one Done can add several previously missing subscriptions, and one device can need several attribute subscriptions. The script reports and never infers inertness from a missing row, which keeps it consistent with `device-lifecycle`'s command-only-consumer contract. `group_by_attribute` emitted `null` for a row with no `typeId` while `device_ids` correctly skipped it, putting a value in the JSON that no caller can act on; Copilot caught that. A second defect was worse: `typeId` was compared raw, so a hub rendering it as the decimal string `"1611"` made a correctly-subscribed device read as absent and the script would then print a confident, wrong "re-open the app's config page and press Done". It now normalizes through the same rule as `hub_device_usage.py._device_id`, which also handles Rule Machine's `1612:Motion` state keys. The `+1` phrasing survived one round in `playwright-ui.md` gotcha 43 after being fixed in the rule and the skill — cross-artifact consistency is the thing a partial fix quietly breaks, and the reviewer caught it.
- **An installed app's "use all X" setting is a snapshot taken at Done, not a live filter** (`rules/app-lifecycle.md`, `rules/ui-automation.md`, `skills/sensor-onboarding/SKILL.md`). `app-lifecycle` covered the **author** side of subscriptions well and said nothing about the **operator** side: how to tell whether an app already installed on the hub is actually watching the device you just added. Grounded 2026-08-30 on 2.5.1.169, adding a leak sensor with Hubitat Safety Monitor installed. HSM reports `appSettings useAllWater = 'true'` and `appState hasWater = "All leak and water detectors"`. Both read as automatic coverage. Neither is: HSM enumerates **per-device** subscriptions and freezes them at the last Done, so the new sensor was absent from `eventSubscriptions`, `waterHandler` never fired for it, and the configured alert never sent. The sensor was still unsubscribed 15+ minutes after being authorized on the mesh, on the dashboard, and in HomeKit — it read `dry` everywhere, the dashboard tile was green, HomeKit showed the accessory, and the alert path did not exist. HSM has no `scheduledJobs` and only two LOCATION subscriptions (`mode`, `hsmSetArm`); nothing re-subscribes on its own. `eventSubscriptions[].typeId` is the only honest statement of what an installed app watches — the same shape as the earlier finding that `appsUsing` is a blast-radius list rather than a liveness list. `useAllSmoke` is assumed to behave identically and is recorded as **unverified** rather than asserted. The reviewer pushed back twice on over-generalization here and was right both times: the first draft claimed `eventSubscriptions` was "the only honest statement of what an installed app watches" (which contradicts `device-lifecycle`'s command-only-consumer contract, where absence is *not* evidence) and that "every built-in app's use-all toggle" is a snapshot (established for HSM's `useAllWater` alone). Both are now scoped to what was measured, with the broader shape flagged as untested. `sensor-onboarding` gains a Step 10 that re-Dones every app expected to watch the new sensor and verifies that the sensor's device id is present in that app's live subscriptions, which is exactly the step that session would otherwise have shipped incomplete. Closes #130.
- **Committing an installed app's config is a UI Done, and the HTTP shortcut is destructive** (`rules/ui-automation.md`, `skills/_reference/playwright-ui.md`). `grep -n "btnDone\|_action_update" rules/ui-automation.md` returned nothing: the rule's framing is "Reach for HTTP first" and it listed the operations with no endpoint without naming the single most common one. This is the one place the HTTP-first preference should lose, and saying so is what stops an agent talking itself toward `_action_update` and then stalling when it correctly rejects it. `_action_update` is **not** the counterpart of the `_action_remove` route: `_action_remove` is branched on *before* settings are applied, which is what makes its documented minimal body safe, whereas `_action_update` **applies** settings and clears anything omitted — on HSM that form carries 69 settings including two 30-device `contactSensorsAway`/`contactSensorsNight` lists that arm the intrusion alarm, so a mis-serialized replay disarms the house silently. Two playwright-ui gotchas land with it. **42:** a locked automation profile is a stale process to clear, not a hard stop — Playwright MCP's "Browser is already in use" plus the extension's "not connected" read together as a live operator session that must not be disturbed, and the process tree settles it in one command (throwaway `ms-playwright-mcp` profile + `playwright-mcp` node ancestor = safe to kill; the default profile is the operator's). **43:** HSM's Done sits in a row of destructive decoys — `settings[armedAway]`, `settings[armedNight]` and `settings[disarmAll]` are live side effects in the same button row, the same hazard as RM's `settings[runAction]`. Match on `name="_action_update"` / `id=btnDone`, never position, never visible text. Verify at the app's live subscriptions rather than on the page — on the grounded run the sensor's id appeared among the `water.wet` subscriptions (13 → 14) while `armedState` stayed disarmed and both 30-device contact lists stayed intact, which is what says the Done committed the intended change and nothing else. The assertion that shipped is **presence of the expected device id**, not that delta: an exact `+1` is not generally valid, since one Done can add several previously missing subscriptions and one device can need several attribute subscriptions. Closes #131.
- **An enabled Rule Machine rule with ZERO eventSubscriptions is inert in every mode** (`rules/ui-automation.md`, `rules/device-lifecycle.md`, `skills/_reference/playwright-ui.md`). It reads perfectly on inspection. The cause is a broken Required Expression: `Expression: **Broken Condition**(F) [FALSE]` once you open Required Expression → Edit, and `(Required Expression false)` in the page title. RM subscribes to a rule's triggers only while the RE is true and to the RE's own source always, so **one** subscription in a non-matching mode is the healthy state and **zero** is the broken one — the rule is not even watching the thing that would arm it. Grounded 2026-08-13: a perimeter-bypass rule sat like this for two weeks. Neither `POST /installedapp/disable` off-and-on nor RM's own **Update Rule** button fixes it; a broken token does not heal on re-init. The rebuild path lands as playwright-ui gotcha 44 with the step that silently defeats it: **`Done with this Condition` renders only after a value is selected**, and skipping it orphans the new condition exactly like the old one, producing an empty expression that *also* reports "Required Expression false" — indistinguishable from the original bug, so the natural next move is to repeat the rebuild that just failed. Closes #138. The diagnosis is scoped to a rule **known to carry an event trigger**: an action-only rule invoked by another rule legitimately holds no subscription, so zero is only diagnostic once the trigger role is established from `state.trigDevs` or a `tDev*` setting. The reviewer caught that the first draft would have misclassified action-only consumers.

## 0.1.76 — 2026-08-30

### Added

- **HomeKit export is one HTTP GET, and the owning hub is the one that does it** (`skills/_reference/endpoints.md`, `skills/_reference/homekit-mdns-network.md`, `rules/multi-hub-topology.md`). `grep -c enableDevice skills/_reference/endpoints.md` was `0`; every HomeKit mention was incidental. `GET /hub/homekit/enableDevice/<deviceId>/<true|false>` persists immediately, the HAP DB rebuilds seconds later and the mDNS `c#` generation bumps, and the app's Done is **not** required. Found by reading `changeDeviceAuthorization()` in the bridge app page's JS. Ground truth for what is served is the unauthenticated `GET http://<hub-ip>:21063/accessories`, not the app's `authorizedDevices`, which records what was asked for. The 149-accessory-plus-bridge cap is enforced client-side and on a multi-hub fleet it decides the layout rather than expressing a preference, which is why the owning-hub rule lands in `multi-hub-topology`: the hub that owns the radio exports the device, and a hub-mesh mirror is never exported. That one is a live trap — asked to "add it to HomeKit on the apps hub" the mirror is right there, already looking exportable, and exporting it works; it just lands the accessory on the wrong bridge. Accessory class is capability-derived and not freely settable (a Zooz ZEN switch offers Switch and Button and nothing else, so it cannot be exported as a Lightbulb or a Fan), and HAP strips a trailing `)` from names. Grounded 2026-08-11 on 2.5.1.140 with both bridges paired, re-exercised 2026-08-30 on 2.5.1.169: one GET moved `authorizedDevices` 53 → 54 and the accessory appeared in the HAP DB ~10 s later with its Leak/Temperature/Battery services. Closes #128.
- **A dashboard's whole tile grid is one JSON POST** (`skills/_reference/endpoints.md`, `rules/ui-automation.md`). `rules/ui-automation.md` implied dashboards were UI-only work. They are not: `GET`/`POST /apps/api/<appId>/dashboard/<appId>/layout?requestToken=<rt>` round-trips the entire layout object, found in `/ui2/dashboard2/js/app.js`'s `saveLayout`. The app id appears **twice** in the path, which the UI URL does not suggest. Two different tokens, and mixing them fails with `Invalid request token`: `Bearer` is the dashboard's `access_token`, `requestToken` is `javascriptRequestToken` scraped from the page HTML and explicitly **not** `parentToken`, which is present on the same page and rejected. Edit only `tiles` and send every other key back or the POST defaults them. Also records what a **`?` tile actually means** — the `template` names an attribute the bound `device` does not have, which reads as a dead sensor and is not one. The grounding case: a `water` tile bound to a Zooz ZEN76 wall switch, showing `?` for months, because the leak sensor it was meant for did not exist yet and the switch shared the location prefix in its name. The `?` was an unmonitored location, not a fault report. Verified non-destructive on 2.5.1.169: a single-field edit left 15 tiles unchanged in count, zero non-tile key drift, zero change to the 14 untouched tiles. One observation is recorded as unexplained rather than theorised — a freshly `createLinked` mesh mirror appeared in `devicesPicked` on 6 of 7 dashboards with no action taken, and the mechanism was not identifiable from HTTP. Closes #129.
- **`configure/json/<id>/<page>` is not a free read — a wrong page name bills a human** (`skills/_reference/endpoints.md`, `rules/ui-automation.md`). A page name the app does not define logs an `ERROR` **against that app**: `Cannot find page 'meansPage' for app 1230`. On a hub running an error-notifier app that is a push notification to a person, naming a real app and reading exactly like a genuine fault in it — three probes produced three Telegram alerts that took real time to explain and dismiss (2026-08-30, 2.5.1.176). So the tempting cheap loop over plausible page names is a page-existence oracle whose negative result is a user-visible alarm. It is also useless: all five probes returned no settings at all, the two *valid* page names included. The correct enumeration is the rendered DOM's `_action_href` buttons, which returned Room Lighting 1230's real structure directly with no guessing and no error log. Two traps beside it: match on the `_action_href` prefix rather than the full `_action_href_name|...` literal (the Device Status Announcer's group page is `_action_href_pageCustomDeviceGroup0Href|...`), and `mainPage` is **not universal** — app 329 names its page `pageMain`, and a tool assuming `mainPage` fires the same logged ERROR. `ui-automation` gains the boundary this draws: HTTP-first does not license guessing endpoint paths. Closes #142.
- **`GET /hub2/appsList` is a TREE, and a flat read misses most of the hub** (`skills/_reference/endpoints.md`, `rules/device-lifecycle.md`). The reference already warned about this for `/hub2/devicesList` ("Iterating `devices[]` flat misses every child device") and said only "Installed apps + `systemAppTypes`" for apps. Measured 2026-08-30 on 2.5.1.169 across three hubs, top-level `apps[]` vs walking `children[]`: **37 → 186**, 9 → 13, 6 → 9. On the busiest hub **80% of the apps are children** — every Rule Machine rule is a child of the RM parent and every dashboard a child of `Hubitat® Dashboards`, so a flat iteration audits neither. This bit a real audit of "which apps reference device X": scanning the 37 top-level apps returned a clean bill and walking the tree to 186 found the references. That is a confident false negative on the exact question `device-lifecycle` Enumerate before removing exists to answer, which is why the rule gains the cross-reference. `appsUsing` on `fullJson` is unaffected — the hub computes it; the trap is only in hand-rolled censuses, which is what you write the moment the question is "which app *setting* contains this id". Closes #132.
- **The Hub Mesh read side: `availableLinkedDevices` vs `localLinkedDevices`** (`skills/_reference/endpoints.md`, `skills/_reference/playwright-ui.md`). The write side was already documented prominently (`addToMesh` on the source, `createLinked` on the destination, sharing is two-sided, `hubMeshFullRefreshNow` does not link). The read side that says *which half is missing* was not, so the half-done state was diagnosed by guesswork. Grounded 2026-08-30 on 2.5.1.169: three freshly shared probes read `meshEnabled: true` / `meshFullSync: true` on the source and had no mirror on the destination. The source-side fields were byte-identical to a working sibling, so the source looked correct and was — the tempting and wrong conclusion is that sharing failed there. One read settled it: all three sat in `availableLinkedDevices` with `linkedLocally: false` while the peer's `hubList[].deviceIds` listed all three. Advertised, not linked. Also records the UI trap on that page as playwright-ui gotcha 41: the Linked-devices `+` opens a PrimeVue confirm dialog whose `.p-dialog-mask` swallows the next click, so the first `+` reads as a dead control and the *next* action times out somewhere unrelated; the reject button carries `p-button-primary` and the accept carries `p-button-text`. Closes #133.
- **`skills/_reference/hub-load.md`** — hub load diagnosis, previously uncovered, where every obvious reading misleads. ### Added

- **`battery = 1` on a Z-Wave sensor is the low-battery flag, not a reading** (`rules/state-vs-attributes.md`). Nothing in the rules warned that an attribute's value space can mix a measurement with a reserved sentinel value. Z-Wave's Battery command class encodes "battery low" as the reserved level `0xFF` (a sentinel value, not a separate bit), and the driver flattens it into the same `battery` attribute the percentage uses, so the number and the warning fight over one slot. ## 0.1.15 — 2026-07-16

### Added

- **`e.statusCode` throws NPE from inside its own getter on 2.5.1** (`rules/groovy-gotchas.md`, closes #25). From a real four-day outage of a large cloud-connected community app. A failed `httpGet`/`httpPost` can raise an `HttpResponseException` whose internal `response` is null; `getStatusCode()` dereferences it, so **reading the status throws**. Safe navigation does not help — `e` is not null, and `e?.statusCode` still enters the getter — so the NPE escapes the `catch` and every recovery below it is dead code, silently. The consequences are the reason this is the file's headline: an OAuth token expiring hourly, a refresh path that could never run, and a manual re-login that bought exactly one hour, every time. It gets worse than the crash: `e.response?.data` is null for the same reason, so the standard community `(500 && code==14)` test **cannot match on this platform even after the NPE is stopped** — fixing the crash alone leaves the bug. Version scope is stated as honestly as it was reported: seen on 2.5.1.125 and 2.5.1.128, not on 2.5.0.159, correlation across one hub rather than a bisect. `/hub/eventsJson` corroborates the timing independently — the measured hub's firmware timeline runs 2.5.0.159 → 2.5.1.121 on 2026-07-07, days before onset — which is the new endpoint doing the exact job it was added for.

A name compared raw does not match.

Correlating an app's log line against an event across the two silently mis-orders by the hub's offset: you conclude a handler never fired when it fired five hours "earlier". ### Changed

- **A status is not a fact** (`skills/debug`). Three wrong diagnoses in one session, all the same error: trusting a rendered indicator over a timestamp. `rules/zwave-zigbee-mesh.md` has carried this for radios since 0.1.7 ("only the probe is evidence"); it generalizes, and Step 4 now says so — prefer timestamps to indicators, verify an action by re-reading what it changed rather than the app's own "I did X" line (emitted when the command is *sent*, not when it lands), and treat a frozen attribute as the trap it is, since attributes hold their last good value rather than going null and a dashboard reads plausible while the integration is dead. Step 5 adds the reporting discipline the outage earned: separate proven from inferred.
- **GString keys in `state[...]` are safe, and the belief that they are not is the expensive part** (`rules/groovy-gotchas.md`). This looks like a defect, is widely believed to be one, and is not — documenting it saves the next person the hour it cost. Verified on Groovy 2.5, closest available to the hub's 2.4: GString and String really do hash differently (the Groovy docs' warning is real), and an explicit `map.put("pending${zone}", v)` genuinely misses on `get("pendingKitchen")` — that is the actual trap. But the subscript operator normalizes the key to `String` **on write**, so `state["pending${zone}"]` survives `state`'s JSON round-trip and a later GString lookup hits. The warning applies to `put` and map literals, not to the idiom every app uses.

Stated alongside the existing Platform-Bound framing: a green suite is evidence about the code under test, never about the harness or the plumbing around it.

## 0.1.11 — 2026-07-16

### Added

- **Route fan-in: a repeater's blast radius** (`zwave.route_fan_in`, closes #22). `hub_mesh.py` ranked and flagged per-node and never asked how many nodes depend on a single repeater. On the grounded hub, **12 nodes route through one repeater the hub has never heard from** — 12 devices whose path runs through something there is no evidence is alive. `never_heard` has surfaced that repeater since 0.1.7, listed identically to a silent leaf in a spare bedroom, and the difference between them is twelve nodes. Nothing in the output said so. It does now: each node carries a `dependent_count`, so a `never_heard[]` entry states its own blast radius inline where the reader already looks, and `route_fan_in.load_bearing_concerns[]` crosses fan-in with the repeater's own health (`never_heard` / `FAILED` / weak-signal / packet errors), ranked worst-first.
- **Fan-in is context, not a fault — and reaches neither counter.** The model is `shared_device_count` on a hub-mesh peer, which informs a re-add's blast radius without ever being a finding of its own. A repeater carrying 12 nodes is a **normal, healthy mesh**; counting repeaters would warn about healthy hubs and teach the reader to ignore the number. Every repeater fan-in marks as a concern is *already* counted through the flag it mirrors — the never-heard repeater warns once, via `never_heard` — so counting it again would double-count one node twelve ways. Fan-in changes what an existing flag **means**, not how many there are. Ranked, never thresholded: Hubitat publishes no "too many dependents" cutoff and this invents none. **Classic mesh only** — LR is a star with no repeaters, so LR nodes are excluded and carry `dependent_count: null`, the question not applying being distinct from zero.
- **Fresh dependents are evidence a flagged repeater still relays.** A repeater cannot be dropping everything while a node behind it reported a minute ago — the rule and skill now say to read the dependents' freshness before blaming the hop. The `mesh-health` eval fixture is built to exercise exactly this: all three of its repeaters carry a fresh device alongside frozen ones, so `route_fan_in` actively refutes "the repeater is dropping traffic" instead of merely not raising it.
- **Incoherent routes are surfaced, never guessed at.** A coherent route runs hub (`01`) → node, through classic-mesh hops only; anything else is a stale or malformed record, and inferring which hops are repeaters out of it would invent dependents. Those land in `route_fan_in.anomalies[]`, and a hop naming a node absent from `nodes[]` is tagged `unknown_node` — data gaps, not mesh faults, in the shape `unparsed_timestamps` already established. This is not hypothetical: the pre-0.1.10 fixture carried exactly that incoherence on 20 of 21 nodes, and fan-in would have read it as one shade repeating for the entire mesh. **A route naming a Long Range or reserved-range id as an intermediate hop is incoherent by the same standard** — a star node relays nothing, so the hop is an anomaly rather than a repeater discovered. Routes are validated before any counting: a route rejected halfway would leave its earlier hops credited with a dependent from a path just called impossible.

## 0.1.7 — 2026-07-16

### Added

- **The command path is now a first-class axis of mesh diagnosis.** Grounded on a live outage: every Z-Wave *and* Zigbee actuator on one hub (22 shades, lamps, an outlet) went dead for 13.7 h while sensors kept reporting — and `hub_mesh.py` said `critical: 0, warnings: 0`. The cause was not a radio at all. The hub's hub-mesh peer record for its companion hub still held an IP from the owner's *previous house's subnet*, so commands crossing the mesh were accepted, logged by the app, and silently dropped. The hub reported that dead peer as `active: true, offline: false, warning: null` with `lastActive` ticking every few seconds. No radio metric can see this class of fault, so `hub_mesh.py` now analyzes `GET /hub2/hubMeshJson` (newly documented) beside the two radios: peers are probed for reachability and identity (`hubUID` in `/hub/details/json` is the same identifier as `hubId`, verified across three hubs — so a reassigned address is caught as well as a dead one), and `hub_mesh.problems[]` rolls into `summary.critical`. Replaying the outage's captured bytes through the new code yields `critical: 1 / peer_unreachable` where the shipped code said all-clear. Each problem carries `shared_device_count`, the blast radius of a re-add — the asymmetry mattered live: the broken link shared 3 devices (cheap to re-add) while the *other* direction shared 148, whose removal would have unbound every app using them.
- **Z-Wave node staleness** (`age_seconds`, `stalest`, `never_heard`), the Z-Wave counterpart of `zigbee.stalest`, and the signal that actually cracked the outage. `lastTime` means "when the hub last heard this node"; for a device that only transmits *after* being commanded, that is "when a command last landed". Ranked, never flagged — silence is not a fault, and reading it needs context the script does not have. `never_heard` catches nodes the hub has never heard at all, which are reported `nodeState: OK` and pass every FAILED-keyed check (6 live on the Devices hub, including a repeater carrying 12 nodes' routes).
- **The actuator-vs-reporter split** in the `mesh-health` skill and the `zwave-zigbee-mesh` rule — the reasoning the outage turned on, and the diagnostic worth more than any single flag. Reporters (lock, motion, presence) transmit on their own, so fresh means the radio works; actuators (shade, outlet, lamp) transmit only when commanded. Reporters fresh + actuators frozen ⇒ the *command* path is broken, not the radio — and when it spans both radios at once, no radio fault can explain it, because two radios do not fail in the same second. A cluster of actuator timestamps in one narrow window is the last moment commands worked (here, a 53-second sunset routine, the outage's high-water mark).

### Fixed

- **`mesh-health` reported a confident false all-clear.** Step 2 said that if `summary.critical` and `summary.warnings` were both 0, "report the mesh looks healthy and finish" — so against 22 dead actuators the skill was engineered to stop the operator looking. Zero counters no longer license an all-clear: a new Step 4 splits the staleness rankings by actuator vs reporter, and only a run that survives *that* may report healthy. The rule and skill now open by stating that a clean radio is not a working device, since every radio metric describes a path commands do not travel.
- **A Zigbee-only run no longer warns about Z-Wave timestamps** (PR #18 review). `/hub/details/json` exists only to date Z-Wave's naive stamps — Zigbee's `lastActivity` carries its own offset — but it was fetched unconditionally, so `--radio zigbee` against a firmware lacking it raised a `fetch_warning` about node ages that run never computes. Since the skill reads any fetch warning as a blind axis blocking an all-clear, an irrelevant warning is a *false* blind axis. The fetch is gated on the Z-Wave path.
- **A peer answering 200 with JSON but no `hubUID` read as identity-verified** (PR #18 review) — `hubId: None` with `error: None` is the one shape that must never look checked-and-fine. It now carries an explicit identity-unverified error like the other unverified cases.
- **The peer probe no longer conflates reachability with identity** (caught independently by both PR #18 reviewers). `probe_peer` treated any `HubError` from `/hub/details/json` as `reachable: false` — but that endpoint is itself undocumented and version-sensitive, so a peer answering HTTP without it would have rolled a false `peer_unreachable` **critical** against a perfectly healthy peer. The two are now separate questions: `reachable: false` is reserved for a connection-level failure (nothing answered), while an HTTP response lacking or not parsing `hubUID` is reachable-with-identity-unverified, which `analyze_hub_mesh` reads as no evidence rather than as a mismatch. Re-verified against the real dead address from the outage: still `critical: 1 / peer_unreachable`.
- **Script runtime floor raised to Python 3.9+** (`scripts/README.md`), which `zoneinfo` requires and the previous documented 3.8+ contract would have broken at import. Guarding the import and degrading to UTC was the alternative and is worse than a clear ImportError: it silently overstates every zwaveJS node's age by the hub's UTC offset — precisely the bug the zone lookup exists to fix. Python 3.8 reached end-of-life on 2024-10-07 and CI runs 3.11. The stale `3.8-compatible` comment in `hub_mesh.py` is corrected to match.
- **Auxiliary endpoints no longer sink the radio diagnostics** (caught by the OpenAI policy reviewer on PR #18 as an `error-handling` Graceful Fallback violation). `/hub2/hubMeshJson` and `/hub/details/json` are undocumented and version-sensitive, and the first cut fetched them in the same fatal `try` as the radios — so a hub or firmware lacking either returned nothing at all, though `analyze()` already models `hub_mesh=None` and `naive_zone(None)` already has a fallback. Non-zero exit is now reserved for the requested radio endpoints; an auxiliary miss degrades the affected key to null and lands in a new `fetch_warnings[]` (and stderr) naming its own `consequence`. Degraded loudly, never silently: a null `hub_mesh` leaves a command-path fault unruled-out, so the skill treats a fetch warning as a blind axis rather than an all-clear. `main()` now takes `transport=` for injection, matching `hub_device_usage.py`.
- **`never_heard` misclassified unparseable timestamps** (caught by Copilot on PR #18). It keyed on `age_seconds is None`, which `parse_ts` also returns for a `lastTime` that is *present but malformed* — inventing "the hub has never heard this node" out of a parse failure, and inflating warnings now that `never_heard` counts. It keys on the raw field's absence; a present-but-unparseable stamp surfaces separately as `unparsed_timestamps[]`, a data anomaly rather than a mesh fault.
- **Flagged Z-Wave warnings never reached the rollup.** `analyze()` counted only `failed` and `packet_errors`, so `weak_signal_heuristic` (and the new `never_heard`) were computed, returned, and dropped from `summary.warnings` — a hub with routes flagged at/below the noise floor still rolled up `warnings: 0`, which the old Step 2 read as healthy. A second false all-clear, independent of the hub-mesh one and the same bug class. Found while verifying the claim that the legacy RSSI floor went unflagged: it does not — the floor works and had flagged two live nodes at `-4dB` and `0dB`; the rollup was throwing their verdict away. Live on the Devices hub, `warnings` goes 0 → 8.
- **Naive `lastTime` stamps were read as UTC, aging every zwaveJS node by the hub's offset** — a third backend trap beside the `lwrRssi` scale. The legacy backend stamps `lastTime` with an explicit `+0000` (true UTC); the zwaveJS backend emits a *naive* stamp in the hub's *local* zone. Measured live: a 70-second-old node read as 5.02 h on `America/Chicago`. Left unfixed, the staleness feature above would have been fiction on half the fleet. `parse_ts` now takes the zone, fetched from the hub's own `timeZone` rather than assumed from whatever machine the analyzer runs on.
